SpotPay is the payments app we’re building. The repo is still called spot-trade, which is why that name shows up in the code and in the screenshots. It’s a pnpm + Turborepo monorepo with an Express 5 + TypeORM backend, a React + Vite desktop client, and an Expo mobile client.

This post collects six insights I screenshotted in March 2026 while adding Stripe subscriptions (PR #53, “Subscription Service”). Most are terminal screenshots of sessions with an AI coding assistant, where an explanation, a plan, or a mistake made something click. For each insight I pull out the lessons the screenshots teach.

The screenshots are from March and the code kept moving, so I also checked each one against main as of 2026-10-31. Where the code has since changed, or a screenshot turned out to be wrong, there’s an Update box. The original screenshots, and the prompt that produced this post, are in the collapsed block at the bottom.

Insight 1: Adding a feature that impacts users

Screenshots 1a to 1d are the plan the assistant produced for “add subscriptions”: a todo list, a phased plan, the manual steps, and a test plan.

Lesson 1: A user-facing feature touches every layer

The todo list (1a) has 16 items, and only a few of them mention Stripe. Grouped by layer:

Layer Items from the todo list
Data model Add stripe_customer_id to the User entity; update the User DAOs and mappers; add updateSubscription to UserService
Client auth state Add email to AuthContext
Config Add STRIPE_WEBHOOK_SECRET to config
UI Update prices in SubscriptionOptions; wire up the Subscribe button
API StripeWebhookController; SubscriptionService; the subscriptions OpenAPI schema; register the controller in server.ts; the portal session endpoint
Clients ManageSubscription desktop component and mobile screen
Safety net Handle edge cases; integration tests

Write the blast radius down before the first line of code. Some of these items look unrelated but are load-bearing. email in AuthContext is the best example: the Subscribe button sends the user to Stripe with ?prefilled_email=, and when Stripe’s webhook comes back, that email is what ties the payment to a row in our users table (handleCheckoutCompleted looks the user up by it). After that first link, stripe_customer_id takes over as the key. So the first design question wasn’t “how does Stripe work?”, it was “what’s the join key between Stripe’s world and ours?”

Lesson 2: Build bottom-up, in phases

The plan (1b, 1c) has four phases:

  • Phase 0, Foundation: the stripe_customer_id column with an index, types and mappers, updateSubscription and findUserByStripeCustomerId, email in the auth state and the sign-in response, the webhook secret in config and docker-compose.
  • Phase 1, Subscription page: real prices and a Subscribe button that passes the user’s email.
  • Phase 2, Webhook backend: the webhook controller with signature verification, the subscription service, shared plan definitions, the OpenAPI schema, rawBodyControllers in app.ts (Insight 3), and server.ts restructured to initialize services after the DB connects.
  • Phase 3, Manage Subscription: the portal-session endpoint, plus the desktop component and the mobile screen.

Each phase only depends on earlier ones, and Phase 0 changes nothing the user can see. It’s the plumbing everything else leans on, which is why it goes first.

Lesson 3: Write the manual steps down

The last block of the plan (1c) is “Manual Steps Required”:

  1. Add STRIPE_WEBHOOK_SECRET=whsec_... to .env, copied from the stripe listen output.
  2. Replace the ******** placeholders in subscription-plans.ts and SubscriptionOptions.tsx with real Stripe price IDs and payment links.
  3. Configure the Stripe dashboard: products, prices, customer portal.

A chunk of this feature lives outside the repo, as state inside Stripe, and no code review will ever see it. Listing those steps is the difference between a plan that works on your machine and one that works on a teammate’s.

Update: that state turned out to be per-environment

The plan doc in the repo records what happened next. The Payment Links and price IDs are not single values: getPlans(env) in packages/shared/types/subscription-plans.ts picks them per environment (local, AWS dev, production), because each Payment Link has its own redirect URL (Insight 2). And a stale build of the shared package once kept serving deactivated Payment Link URLs to the mobile app, which showed up as Stripe’s “this link is no longer active” page.

Lesson 4: A test plan is a spec, and the ❌ rows are the point

The test plan (1d) lists 10 Cucumber scenarios across the two new controllers:

Endpoint Scenario Expected
POST /stripe-webhook checkout.session.completed user becomes active and gets a stripe_customer_id
POST /stripe-webhook customer.subscription.updated plan type changes
POST /stripe-webhook customer.subscription.deleted inactive and free
POST /stripe-webhook invoice.payment_failed logged, 200
POST /stripe-webhook missing stripe-signature 400
POST /stripe-webhook unknown event 200
POST /subscriptions/portal-session success returns { url }
POST /subscriptions/portal-session missing returnUrl 400
POST /subscriptions/portal-session no stripe_customer_id 400
POST /subscriptions/portal-session unauthenticated 401
  • The ❌ marks aren’t failing tests. They mark scenarios that expect an error status, and I almost misread them. Four of the ten are error paths, which is what makes it a plan and not a demo.
  • Unknown event returns 200 because that’s Stripe’s convention: acknowledge everything, act only on the event types you care about. (The feature file has a comment saying exactly this.)
  • It reuses an existing seam instead of inventing one. The Stripe fakes are switched by an env var in server.ts, the “same pattern as MOCK_GOOGLE_SERVICE”.
  • Reviewing the plan is the cheap checkpoint. The menu at the bottom of the screenshot (accept and build, accept with default permissions, exit and prompt myself, suggest changes) is that checkpoint. Correcting ten bullets costs far less than correcting a diff of dozens of files.

Today the feature file has 12 scenarios: these 10, a check that the mobile deep-link bridge page is served, and an end-to-end checkout-then-portal flow.

Insight 2: Payment Link vs Customer Portal

Screenshots 2a to 2c came from a puzzle in the desktop app: Stripe’s Manage Subscription page has a “Back to spot-trade” button, and the Subscribe page doesn’t.

Lesson 1: They’re two different Stripe products

In 2a I asked what URL the Subscribe button’s href={plan.link + '?prefilled_email=' + encodeURIComponent(email ?? '')} actually goes to. There are two separate Stripe URLs in the app:

  • plan.link (in SubscriptionOptions) is a Payment Link (https://buy.stripe.com/...), for new subscribers to check out the first time. ?prefilled_email= pre-fills the email field.
  • url (in ManageSubscription) is a Customer Portal URL (https://billing.stripe.com/session/...), for existing subscribers to cancel, change plan, or update their payment method.
Payment Link Customer Portal session Checkout Session
For new subscribers existing subscribers new subscribers, or one-off payments
Created by hand in the Dashboard, a static URL by the API: stripe.billingPortal.sessions.create() by the API: stripe.checkout.sessions.create()
Where the user goes afterwards set per link in the Dashboard (“After payment”) returnUrl, passed per session success_url and cancel_url, passed per session
Prefilling ?prefilled_email= in the URL n/a, the session is created for a known customer customer_email

Lesson 2: Static link or per-request session? That decides where the config lives

In 2b I asked why the Portal has a “Back to spot-trade” button and the Subscribe page doesn’t. The portal session is created through our API, and we pass it a returnUrl, so Stripe knows where “back” is. A Payment Link is a static URL with no returnUrl parameter. Where the customer lands after paying is configured in the Dashboard, per link. If you want per-request control, switch to API-created Checkout Sessions, which take success_url and cancel_url.

The general lesson: with a static Dashboard object, the configuration lives in Stripe. With an API-created session, it lives in your code, where it’s versioned and reviewed. Payment Links are the quickest way to start charging, but you trade that control away.

Lesson 3: Dashboard config is environment state

2c is the Dashboard side of the same story: the Payment Link editor’s After payment tab, set to “Don’t show confirmation page” and redirecting to http://localhost:5174/manage-subscription. That URL lives in Stripe, not in git, so every environment needs its own link: a localhost one for local dev, another for the deployed dev environment, another for production.

Update: that’s exactly how it played out

The plan doc says getPlans(env) selects Payment Links per environment, “and therefore in each link’s configured ‘After payment’ redirect URL”. On mobile the redirect has to land back inside the app, so the link points at a small backend bridge, GET /subscriptions/success, which serves a page that bounces into the app through the spottrade://subscription-success deep link. One-off invoice payments take the other route from Lesson 2: they use API-created Checkout Sessions (mode: "payment").

Lesson 4: Payment Links mint a new Customer every time

One more consequence of the static-link approach: every completed Payment Link checkout creates a fresh Stripe Customer, even for someone who has subscribed before. A user who cancels and re-subscribes three months later (an edge case from the original plan) would strand their old customer, and any still-active subscription on it would keep billing. So handleCheckoutCompleted links the new customer first, then deletes the superseded one (deleting a customer cancels its subscriptions). If the delete fails it’s logged but non-fatal.

Insight 3: Raw-body controllers

Screenshot 3a is a few lines of app.ts, and the comment in it is the lesson: some routes need the raw JSON, so they can’t sit behind middleware that parses JSON into objects.

Lesson 1: Signature checks need the exact bytes

Stripe signs the raw request body. stripe.webhooks.constructEvent(body, signature, secret) recomputes the signature over whatever you hand it. Parse the JSON and re-serialize it and you get equivalent JSON but not identical bytes (whitespace, key order), so verification fails. The SDK doesn’t even attempt it if you pass a parsed object: the installed version (18.5.0) throws “Payload was provided as a parsed JavaScript object instead”.

Lesson 2: Mount order is the whole game

Express body parsers consume the request stream, so whatever is mounted after bodyParser.json() sees req.body as an object. SpotPay’s App takes two separate lists to make that ordering explicit:

// app.ts: raw-body controllers are mounted first, then the global middlewares
if (appInit.rawBodyControllers) {
  this.routes(appInit.rawBodyControllers);
}
this.middlewares(appInit.middlewares); // bodyParser.json(), urlencoded, cookieParser, openApiValidator
this.routes(appInit.controllers);
// server.ts (simplified): the webhook controller goes in the raw-body list
const app = new App({
  port,
  rawBodyControllers: [new StripeWebhookController(/* ... */)],
  controllers: [/* everything else */],
  middlewares: [bodyParser.json(), /* ... */],
});
// stripe-webhook.controller.ts: the route itself asks for a Buffer
this.router.post("", express.raw({ type: "application/json" }), this.handleWebhook);

Turning the constraint into a named constructor parameter means the next raw-body route (another provider’s webhooks, say) has an obvious place to go, and nobody has to remember the rule.

Lesson 3: Mounting early means skipping what comes later

A raw-body controller never passes through the global middlewares: no JSON parsing, no cookie parsing, and no express-openapi-validator. That’s fine for the webhook, because the signature is the authentication, but it means the handler has to validate for itself. It does: it checks the header, verifies the signature, and falls through to a default: case for events it doesn’t know.

Nothing in the test suite guards the mount order

If someone moved the webhook controller below bodyParser.json(), the integration tests would stay green while real webhooks started failing with a 400. The reason is in Insight 5, Lesson 3.

Insight 4: The webhook flow

Screenshot 4a shows two things in one terminal: the assistant “simplifying” handleCheckoutCompleted so it only sets stripe_customer_id and subscription_status: "active" (leaving the plan type to handleSubscriptionUpdated, and deleting resolveSubscriptionType and its extra Stripe API call), and then my follow-up, “When is handleSubscriptionUpdated called?”

Lesson 1: Each event has one job

The assistant’s answer separates two jobs, and the separation is useful on its own:

  • checkout.session.completed says who paid: the Stripe customer ID and email. It’s where we link Stripe’s customer to our user.
  • customer.subscription.* says what state the subscription is in: plan, status, renewal.

For a new subscriber the screenshot concludes that both events fire: the first links the customer, the second sets the plan type and status.

Lesson 2: An AI’s account of an API is a hypothesis

Item 1 in the assistant’s list says customer.subscription.updated fires when “a new subscription is created (right after checkout.session.completed)”. Stripe has a separate event for that, customer.subscription.created. In March the controller had cases for .updated and .deleted and none for .created (I checked the controller as of PR #53). The result, in the words of a code comment added later: created “used to be unhandled, which is why subscription_type stayed ‘free’ after a first-time subscribe”. PR #63 (2026-10-01) added it.

The lesson isn’t “don’t trust the assistant”. It’s that any explanation of someone else’s API, from an AI or a blog post, is a hypothesis until you’ve seen the events arrive. stripe listen prints each event as it forwards it, so the real sequence is a few seconds away, and it’s worth checking before deleting code on the strength of the explanation.

Lesson 3: The simplification was the bug. Give the state one owner

In 4a, removing the “extra Stripe API call” made handleCheckoutCompleted depend on a second event arriving to fill in the plan. Today there’s a single writer, applyStripeStateToUser, which re-reads the customer’s subscriptions from Stripe and writes subscription_status, subscription_type and subscription_expires_at:

Event What the payload is used for Handler today
checkout.session.completed (subscription mode, platform account) who paid: customer ID and email link stripe_customer_id, then applyStripeStateToUser
customer.subscription.created, .updated, .deleted which customer’s subscription changed one handler, handleSubscriptionLifecycleEvent, then applyStripeStateToUser
invoice.payment_failed a payment failed logged (retry and notification are still TODO)

The payload only identifies which customer changed. The new state always comes from a fresh read. The reason, quoted from Stripe’s docs in the code comment: “Make sure that your event destination isn’t dependent on receiving events in a specific order.” An older updated can arrive after a newer one, and acting on its payload would write stale state over fresh state. Re-reading converges on the same answer whatever the order and however many redeliveries. A POST /subscriptions/sync endpoint exposes the same reconcile as a repair path for a webhook that never arrives.

Update: delivery is at-least-once, too

Order isn’t the only thing Stripe doesn’t promise. The webhook controller now claims each event ID by inserting it into a processed_webhook_events table before doing any work. The primary-key insert is the lock, so two concurrent deliveries can’t both proceed, and a duplicate is acknowledged with a 200 and skipped. If the handler then fails, the claim is released so Stripe’s retry can reprocess the event.

Insight 5: Testing Stripe

Screenshots 5a and 5b are two halves of a decision about how to test the Stripe boundary in the integration suite.

Lesson 1: Fake the network, not your own code

In 5a I asked why we weren’t using stripe-mock, Stripe’s official mock HTTP server for its REST API. The assistant’s answer: the suite mocked two things, MockSubscriptionService (which fakes createPortalSession()) and webhook signature verification. Since handleCheckoutCompleted and handleSubscriptionUpdated only process webhook data and update the database, stripe-mock would replace the mock for exactly one method, and “adding a Docker container just to avoid mocking a single method probably isn’t worth the added complexity”.

That’s a fair cost-benefit for the code as it was that day. The argument on the other side is that an in-memory MockSubscriptionService replaces the very class under test, so the test ends up proving the mock works. Pointing the real Stripe SDK at a fake Stripe over HTTP keeps our own code (the parameters we send, serialization, the SDK version) in the loop. 5b shows that second decision being carried out:

  • a stripe-mock container in integration-test.docker-compose.yaml (ports 12111 and 12112)
  • SubscriptionService reads STRIPE_API_BASE from config, and when it’s set the SDK points at stripe-mock instead of api.stripe.com
  • MockSubscriptionService is deleted, because createPortalSession() now calls the real SDK against stripe-mock
  • the env var MOCK_STRIPE_SERVICE becomes MOCK_STRIPE_WEBHOOK

Lesson 2: Two seams, two kinds of fake

There are two directions across the Stripe boundary, and they need different fakes:

  • Outbound (we call Stripe): it’s plain HTTP, so a fake HTTP server can stand in. That’s stripe-mock.
  • Inbound (Stripe calls us): webhooks are signed, and a test can’t produce a valid signature, so the verification step is swapped in memory. 5b puts it as “the one thing stripe-mock can’t help with”.

The rename in 5b’s last bullet is a small lesson of its own: a toggle should be named for what it toggles. After the change MOCK_STRIPE_SERVICE would have implied the whole Stripe boundary was mocked, when it only controlled signature verification.

Lesson 3: A fake must be at least as strict as the real thing

The in-memory webhook mock, MockStripeWebhookService, accepts a string, a Buffer, or an already-parsed object (it falls back to JSON.stringify). The real service rejects a parsed object (Insight 3, Lesson 1). That leniency is why the suite can’t notice a broken mount order. A cheap fix, not done yet: make the mock throw on anything that isn’t a Buffer, so a mount-order regression fails loudly in CI.

Lesson 4: A forged event proves your handler, not your assumptions

Integration tests post events we built by hand. They can show that the handler copes with the events we thought of, but not which events Stripe really sends. That’s the Insight 4 bug in a nutshell: subscription.feature has no customer.subscription.created scenario and no duplicate-delivery scenario, and a test written under the belief that .updated is the first-subscribe event would have passed. Keeping stripe listen, or stripe trigger against test mode, in the loop is what closes that gap.

Update: stripe-mock never landed

As of 2026-10-31 none of the 5b change set is in the repo. git log --all -S"stripe-mock" and -S"STRIPE_API_BASE" both come back empty, so it never reached a commit on any branch. integration-test.docker-compose.yaml has no stripe-mock service, MockSubscriptionService still exists, and MOCK_STRIPE_SERVICE still switches all the Stripe fakes in server.ts (the new name survives in one docstring).

The assistant’s cost-benefit also aged. It was right that only createPortalSession() called Stripe in March, but today every webhook handler re-reads the customer’s subscriptions from Stripe (Insight 4). So MockSubscriptionService grew a listCustomerSubscriptions override that remembers what the mock webhooks said about each customer, effectively playing Stripe. stripe-mock is stateless (its README says so: a POST is validated but not stored), so it couldn’t answer “what is this customer’s subscription now?” differently per scenario. For those tests the stateful in-memory fake has a job stripe-mock can’t do.

Insight 6: TypeORM migrations vs synchronize

Screenshot 6a is an explanation of two things that both change the database schema but serve different purposes.

Lesson 1: Two tools, two purposes

  • Migration files (at the time, the SQL files 00001_users_schema.up.sql and its siblings) are explicit, versioned schema history. They let you say “at version X we added Y”, make environments reproducible, put DB changes in PR review, and safely update already-running databases with incremental ALTER TABLE steps. They’re the durable record of schema evolution.
  • synchronize: true (typeorm-config.ts) is an automatic dev convenience. On startup TypeORM compares the entities (for example users.ts) to the live database and mutates the schema to match. That’s fast for local development, but it isn’t a migration history, it isn’t auditable, and it can cause drift across environments.

Lesson 2: A migration only counts if something runs it

Here’s what happened to the repo after that screenshot:

Date What happened
2026-03-17 Screenshot 6a: migrations are history, synchronize is a dev convenience
2026-03-27 PR #53 adds stripe_customer_id: to the entity, and by editing 00001_users_schema.up.sql in place. The 00005_add_stripe_customer_id.up.sql from the plan (1b) was never committed
2026-10-01 PR #63 deletes apps/backend/migrations/
2026-10-31 synchronize: true, unconditional, with a TODO above it

The code comment explains why PR #63 deleted them. The SQL files were only mounted at docker-entrypoint-initdb.d, so they ran when a local Postgres volume was first created and nowhere else. They were never applied to RDS, and they had drifted from the entities. They were deleted once synchronize was confirmed to reproduce the identical schema from scratch.

So the explanation in 6a held up, but the choice that mattered wasn’t “migrations vs sync”. It was “migrations that run vs sync that runs”. Migrations that nothing executes are documentation, and documentation rots. Even in March the SQL was being edited in place rather than extended with new numbered files, which is a sign it wasn’t functioning as incremental history.

Lesson 3: Fence synchronize off before production

synchronize: true now runs in AWS dev and production as well, against RDS. The comment in typeorm-config.ts spells out the risk: on every deploy TypeORM ALTERs and DROPs to make the database match the entities, and “renaming a property can silently drop the old column and its data, with no review and no rollback”. The TODO sketches the fix:

  1. Add migrations and migrationsRun to the data source.
  2. Turn synchronize off outside local.
  3. Generate a baseline migration that returns early when the schema already exists, so environments previously built by synchronize record it instead of trying to recreate their tables.

Takeaways

  1. Write down the blast radius, and the join key between your system and the third party’s, before writing code.
  2. Build in phases from the data model outward, and list the manual steps that live outside the repo.
  3. Know whether you’re holding a static Dashboard object or an API-created session. It decides where the config lives and what differs per environment.
  4. A route that needs raw bytes is mounted before the body parsers, and the constraint gets a name.
  5. Treat a webhook as a nudge, not as the truth: re-read the state from the source, and de-duplicate by event ID.
  6. An AI’s explanation of someone else’s API is a hypothesis. Check it against the event stream or the docs.
  7. Fake the network, not your own code. Keep an in-memory fake only for what can’t be faked, and make sure it isn’t more lenient than the real thing.
  8. A migration only counts if the pipeline runs it, and synchronize is a dev convenience that needs a fence before production.
